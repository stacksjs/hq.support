# Knowledge and text AI

Knowledge articles persist in the application SQL database. Public retrieval requires both `published` status and `public` visibility. Agent knowledge access requires active membership of the article's workspace. Only owners and admins may create, import, or edit articles. Edits require the current revision number and preserve immutable revision snapshots. Imports accept a supplied HTML or Markdown document and store plain text; they do not fetch URLs, run scripts, or render imported markup.

Search is **lexical**, not semantic or vector search. It matches up to twelve distinct non-stopword query terms against lowercase title/body using parameterized SQL AND predicates, ranks the first hundred matching rows by title/body matches, and returns up to fifty. Locale and collection filters are available. This implementation works with persisted SQLite and PostgreSQL rows and survives restarts. The native Stacks `VectorIndex` is memory only, so this application does not claim persistent embeddings, pgvector retrieval, or semantic ranking.

The public help API is `GET /api/help/projects/{project}/articles` and `GET /api/help/projects/{project}/articles/{slug}?locale=en`. A public project id is not an agent credential. Widget knowledge and AI APIs require an unexpired project-scoped customer bearer token and an exact configured browser origin. Customer AI additionally verifies ownership of the conversation. Agent copilot uses native Stacks authentication and workspace membership, can retrieve published internal articles, and returns a suggestion without sending it.

AI uses `createAIClient(config.ai)` from native `@stacksjs/ai/client`; provider secrets stay on the server. Configure a supported provider through `config/ai.ts` and the provider's environment credentials. The app's default OpenAI provider requires `OPENAI_API_KEY`. Missing configuration returns `503 ai_unavailable`. Provider failures return an explicit error and release reservations. A model handoff also releases the unit and reply-turn reservation because no AI reply was delivered. No configured provider means no generated answer. A query with no relevant knowledge returns an explicit human handoff without calling a model.

A prompt contains the question plus at most four published article excerpts, bounded to approximately 4,000 UTF-8 bytes. It instructs the model to treat sources and questions as data, answer only from supplied sources, and produce structured JSON citing article ids. The server rejects unknown source ids, missing citations on answers, invalid output, or invalid token accounting. Before publishing, it verifies cited article revisions and visibility again. This grounding narrows the evidence supplied to a model; it does not prove every statement semantically follows from an excerpt. Copilot suggestions should be reviewed by an agent.

Customer answers persist as public messages with source links, and enqueue a durable delivery event in the same transaction as finalization. Run responses include article ids, titles, slugs, locales, revisions, and source URLs. The AI endpoint is `POST /api/widget/projects/{project}/conversations/{id}/ai`; copilot is `POST /api/support/projects/{project}/conversations/{id}/copilot`. Both accept `{ question, idempotencyKey, locale? }` and return `{ answer, handoff, sources, retrievalMode, messageId? }`.

AI admission serializes on the workspace row. The free tier admits exactly ten AI-handled conversation units per UTC month; each conversation unit permits at most twenty reply turns and 20,000 tokens. A conservative token reservation includes prompt UTF-8 bytes, framing allowance, and the provider's 1,024-output-token limit. Finalization replaces it with reported provider usage. A near-limit request can be refused conservatively before the model call. Pending attempts have a durable 90-second owner lease and native requests abort after sixty seconds. Database transactions are not held during provider calls. Completed idempotent retries replay the persisted response; changed input is rejected. Failed requests may retry the same key, while an active request returns `409 ai_busy`. Expired attempts release their unit, turn, and token reservations on a subsequent AI request in the workspace, or through `recoverExpiredAiRuns`.

Acceptance uses real HTTP requests, native registration/login/routes/actions, native generated migrations, and a disposable SQL database. A local OpenAI-compatible HTTP server replaces only the external model provider during tests. No database is mocked. Live model quality, production credentials, semantic retrieval, multilingual relevance, and large-corpus search performance require separate deployment verification.
