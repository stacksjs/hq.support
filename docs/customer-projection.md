# Customer conversation projection

Existing widget list/detail reads share the customer projection with customer mutation summaries. No realtime route, enrollment or browser subscription is added by this change.

`updated_at` means the later of conversation creation and the latest scoped **public message creation time**, in UTC ISO milliseconds. It is not last general conversation activity. Notes, assignment, agent read cursors and private attachment changes do not affect it. Closing/reopening can change public status/deadline without advancing this last-message timestamp. Public attachment/delivery status changes likewise need periodic full-state reads; this is not an event-complete activity clock.

The computed query uses workspace, project, conversation, contact and public visibility predicates. SQLite normalizes each message with `julianday` before taking its temporal maximum and explicitly rounds the result to epoch milliseconds. This accepts imported SQL-space, ISO, explicit-offset and UTC timestamps without comparing mixed lexical formats. PostgreSQL takes `MAX` of its native UTC `timestamp` column; native driver `Date` values normalize to ISO. Import writers must normalize offsets to UTC before binding PostgreSQL's timestamp-without-timezone columns, as existing imports do. Conversation creation is normalized before comparison. General `updated_at` is never a fallback or a backfill source. No public activity column/backfill is needed.

Customer `unread_count` retains the stored customer/public count; agent per-user read counts remain agent-only. Customer contact fields remain own ID/name/email/external ID. Existing numeric IDs and ID-based ordering remain compatible. This does not conceal historical shared-ID gaps on later public insertions.

History detail accepts `beforeMessage`, `limit`, `beforeAttachment` and `attachmentLimit`. Unknown/duplicate keys, noncanonical/nonpositive/unsafe cursors and invalid limits return 422. Messages default to **500**, maximum 500, preserving the current messenger's transcript contract. Attachments default to 100, maximum 100. Attachment pages select the newest visible stored files, then return each page ascending by ID as before; this intentionally bounds the formerly unbounded attachment list for both customers and agents. Message pages retain ascending ID order. Agents retain general activity/routing metadata and internal messages, subject to the same documented detail bounds.

Each SQL query fetches at most the row limit plus one lookahead; attachment reads never fetch all files for later trimming. Customers see only stored public files or their own allowed uploaded files. Private agent files cannot affect metadata, size, count or cursor. The response adds `attachmentsNextCursor`; the existing `messagesNextCursor` and list `nextCursor` keys remain. A non-null cursor always names the oldest/last emitted row in descending retrieval order, never the lookahead or a byte-trimmed row. Use the cursor as `beforeAttachment`, `beforeMessage` or list `cursor` to read older rows. Each page is independent and supplies no realtime checkpoint.

Bounds measure actual serialized UTF-8 JSON, including whole-row commas/brackets: 128 KiB summary arrays, 256 KiB message arrays, 64 KiB attachment arrays, and **512 KiB for the exact final response including contact/conversation metadata and cursors**. Rows are never truncated. A single oversized row or an oversized final metadata envelope returns a generic bounded 503 `projection_unavailable`, without an advancing cursor. Data errors are not silently skipped.

The current messenger boot/refresh/reply code replaces `thread`/`attachments` from detail and does not follow history cursors. The console's `loadHistory()` reads assignment audit history, not transcript history. Keeping 500 avoids an unrelated 50-message regression. Very long/multibyte transcripts can now produce fewer than 500 rows within the byte budget; older messages/files are available through truthful cursors. A later explicit UI ticket must consume those cursors; this change does not claim the UI displays entire large histories.

All ordinary widget responses retain no-store and exact-origin CORS; no ETag/Last-Modified derives from private activity. Privacy assertions compare canonical complete list/detail bodies before and after real authenticated HTTP note, assignment, read, private upload, failed public sharing and deletion. SQL fixtures supply historical imported timestamps and oversized records; public mutation/auth paths use the actual native router. Focused tests run on disposable SQLite and PostgreSQL without a PostgreSQL skip. Missing PostgreSQL is a qualification failure, not proof. The test seam does not qualify SSE, Redis or realtime enrollment.
