# Customer replies to resolved requests

Customer messages on an existing request use one workspace-serialized admission transaction. Open requests accept the message. Snoozed requests always resume the same conversation, regardless of age. A closed request resumes the same admitted conversation when its actual resolution time is at most seven days ago, including the exact boundary. The comparison uses HQ’s trusted server acceptance time: the widget request time captured internally, or a verified provider event’s immutable retained `created_at`. Provider/body timestamps cannot move the window. Delayed processing of an already accepted event keeps that original decision; absent legacy acceptance time uses server now, while malformed/future stored time is refused for recovery. New-request usage always belongs to its actual admission month in UTC, never the source event month. These resumptions never consume a new conversation unit and remain available after a trial or conversation allowance expires.

`Conversation.resolvedAt` records UTC milliseconds only when a status transition actually enters `closed`. A repeated close, assignment change or internal note does not advance it. Moving out of closed clears it. The shared routing writer supplies the timestamp for manual and durable workflow status changes. Customer-supplied timestamps, status, routing and lineage fields confer no authority.

Preexisting/imported closed rows without a trustworthy resolution timestamp keep zero. They receive one quota-free same-conversation reopen, explicitly grandfathered in the metadata intent. The service never guesses the date from `updated_at`. The next real close records a new resolution time. Intercom imports accept `closed_at` or `statistics.last_close_at` only as valid Unix seconds within the exported creation/update interval. Conflicting or contradictory dates remain source-review work. Imports never rewrite a resumed native conversation's status or resolution time.

A customer message more than seven days after a known closure starts a linked new request. The transaction checks the current plan and exact UTC conversation ceiling, creates the successor with that actual first customer message, routes it through the current default inbox, and saves both lineage directions and the idempotency receipt. The old request remains closed. There is no empty placeholder message, implicit overage purchase or separate charge for linking. A failed entitlement/allowance check commits no message, successor, audit, cursor or usage increment. The widget receives the actual refusal and keeps its draft; provider intake keeps the original archived event pending and recoverable.

Concurrent different-key replies to an old request follow its persisted current successor instead of creating competing successors. Same-key retries return the exact original message/destination; changing a committed key's payload is refused. A newly closed successor follows the same rule. Every traversed row must match workspace, project and customer and carry the matching predecessor link. Cycles and chains longer than 64 rows fail explicitly. Refreshing/selecting the current request avoids walking old chains; a channel's inbound pointer already selects the current request.

In-window reopening rechecks its historical assignee against current workspace/team membership, inbox activation, availability and workspace-wide open load through the shared routing engine. Ineligible assignments become open/unassigned with the actual reason. Concurrent resumptions cannot both take the last capacity slot. New successors use normal default-inbox/manual/round-robin admission. Assignment before/after state and metadata-only reopen/continuation outbox intents persist in the same transaction. They are audit intents, not external delivery receipts.

Widget bearer/customer ownership is rechecked under the workspace lock. Its reply response preserves `message` and adds the destination `conversation`, with `continuedFromId` on a newly admitted successor. `message.conversation_id` always identifies where the message actually committed. Summaries expose the resolution milliseconds and nullable predecessor/successor IDs after their existing ownership checks. Private notes do not act as customer messages. Existing project-write-key native SDK replies and workflow replies keep their agent-side behavior; a dedicated server customer-reply API is outside this slice.

## Managed channels and retained operations

SMS, Twilio WhatsApp, Slack, Discord, Meta-normalized text and signed email intake converge on the same customer reply admission. Initial provider signature/account/channel validation remains unchanged. A new inbound message advances the provider thread's current conversation pointer only inside that admission transaction. `ChannelConversation` stores immutable historical request bindings, lazily preserving existing thread associations when they first continue. Sender/contact identity cannot change while following a provider thread. Email reply capabilities remain bound to the original provider thread, exact sender and contact; an unverified From address never merges private histories.

An outgoing delivery's immutable message row owns its conversation context. Dispatch, attachment capability checks, attachment publication and ticket first-response reconciliation use `message.conversation_id`, including pre-migration deliveries. They never infer that target from the thread's current inbound pointer. An agent can still reply to a historical request through its saved provider binding. Advancing inbound state cannot move a delayed send, image capability, SLA receipt or wallet operation to a newer request. Retained inbound media uses the saved admission receipt and historical binding, so restart/recovery preserves its original destination and private customer.

Retention selects replay receipts by their authoritative top-level committed message/conversation destination, even when the reply URL names a predecessor. It reads project-scoped receipts in bounded 100-row keyset pages up to a captured high-water mark inside the retention transaction. Only a genuinely absent destination permits legacy old-URL fallback; malformed or inconsistent stored fields block completion for review. Retaining an old request preserves a newer successor receipt. Retaining the successor removes its content from every old-URL receipt, and retries cannot recreate erased history. This does not publish customer notification intents.

Existing CSAT receipts stay immutable on the original request; a new successor starts with its own conversation-scoped eligibility. Existing AI accounting is preserved when resuming a request, while a successor passes through normal AI admission when actually used. Managed delivery continues to require the configured provider, valid wallet funds/caps and actual provider acknowledgement/cost; reopening grants none of those.

## Retained evidence

`tests/feature/customer-reopening.test.ts` runs actual native authentication, HTTP and generated SQL on disposable SQLite and vector-capable PostgreSQL. Its fixture fixes only the server comparison clock and supplies actual stored historical resolution dates. It exercises exact seven-day edges, snooze/legacy behavior, stale timestamp attempts, SDK agent compatibility, scope/lineage failures, capacity overflow, three independent HTTP server processes racing one successor, process restart replay, expired trials and the 120th/121st Free allowances.

Extended managed-channel and email suites retain real native signed/provider HTTP fixtures, private binary ingestion, queued historical media delivery, delayed reconciliation and immutable bindings. Slack/Discord continuation checks reuse their already-verified normalized source shape at the trusted intake seam. Import tests preserve valid source resolution dates and flag contradictory ones. These are isolated synthetic providers and accounts, not live channel qualification. No shared service is written or restarted.
